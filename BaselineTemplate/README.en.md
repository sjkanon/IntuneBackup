# BaselineTemplate/

The CIPP **baseline** as a file: which packages deploy in which stage, to whom, and when a
tenant moves on.

| | |
|---|---|
| Files | [`Baseline.json`](Baseline.json) (Intune), [`Defender-Office365.json`](Defender-Office365.json) (email), [`Windows-Updates.json`](Windows-Updates.json) (patching) and [`Purview-DLP.json`](Purview-DLP.json) (data leakage) — generated by [`scripts/generate-baseline-template.js`](../scripts/generate-baseline-template.js) |
| Recognised by | `TemplateType: "BaselineTemplate"` and the folder name `BaselineTemplate/` |
| Name in CIPP | `Baseline` |

## Why this lives here

`IntuneTemplate/` supplies the policies, but in CIPP templates just sit there: a baseline is
what deploys them. Filling in that screen by hand means adding the same standard thirteen times and
picking the right assignment target thirteen times — one misclick puts up to 70 policies (the
`[Baseline] - Baseline-Devices` package) on the wrong audience. So this file comes from the same source as the rest of the repo: the manifest.

## What's in it

| Stage | Packages | Moving on to this stage |
|---:|---|---|
| 1 · Now | `[Baseline] - Baseline-Devices`, `[Baseline] - Baseline-Users`, `[Baseline] - Baseline-ADE-token` and the eight group packages `[Baseline] - Baseline-SEC-*` | — stage 1 always applies |
| 2 · Pilot | `[Baseline] - Baseline-Pilot` | everything from stage 1 is compliant (`success`) **and** two weeks have passed (`time`) |
| 3 · Awaiting prerequisite | `[Baseline] - Baseline-Wacht` | `manual` — someone moves it on |

Which policies are in which package is listed in the
[`IntuneTemplate` README](../IntuneTemplate/README.en.md#cipp-packages).

Stage 1 always applies and later stages stack on top of it. The condition belongs to the stage
you **enter**, not the stage you leave. Phase 3 waits for something CIPP cannot measure — a
first phone enrolment — so `manual` is the honest answer there.

## Importing — with the button, not with the automatic sync

Tools → Community Repos → this repo → `BaselineTemplate/Baseline.json` → **Import**. CIPP
turns it into a baseline (not a template row) under Tenant Administration → Baselines.

It arrives assigned to the placeholder tenant `Exported Template`, so nothing deploys until you
pick tenants yourself. That is deliberate — it is the same placeholder CIPP's own export uses.

**That button is the only way.** CIPP has two code paths that read from a linked repo, and
only one of them knows about baselines:

| Path | What it does with this file |
|---|---|
| Tools → Community Repos → Import (`Invoke-ExecCommunityRepo`) | sees `TemplateType: "BaselineTemplate"` and calls `Import-CIPPBaselineTemplate` — becomes a baseline |
| The scheduled template sync (`New-CIPPTemplateRun`) | fetches every `.json` (except under `NativeImport`) and pushes it through `Import-CommunityTemplate`, without looking at `TemplateType` |

In that second path this file has no `RowKey`, no `@odata.type` and no `settings`, so it falls
through every detection and lands as a **nameless row** in the templates table — the same row
the other non-policy files in this repo end up in (deduplication matches on an empty
`Displayname`, so it stays that one row). It does nothing and you can delete it in CIPP.

Consequence for day-to-day use: the policies in `IntuneTemplate/` come along automatically with
the link, the baseline itself you fetch once with the button — and again when it changes, which
the catalogue flags with *UpdateAvailable*. A re-import updates the existing baseline on the
same GUID, so the assigned tenants and the results stay in place.

Putting it under a `NativeImport` path to avoid that nameless row does not work: the catalogue
filters that word out too, and then the file can no longer be found with the button either.

## What you do yourself afterwards

- **Assign tenants.** Without that the baseline runs nowhere.
- **Make sure the groups exist.** `SEC-Baseline-Pilot`, `SEC-Update-Ring1`, `SEC-Update-Ring2`,
  `SEC-Shared-Devices`, `SEC-Android-Dedicated`, `SEC-iOS-BYOD`, `SEC-iOS-Corporate` and
  `SEC-Remote-Support-macOS` must exist in the tenant; CIPP looks them up by name (wildcards allowed).
  These are default names. If a group is called something else, change `faseGroep` in
  [`_manifest.json`](../IntuneTemplate/_manifest.json) — for the pilot group also `PILOT_GROUP`
  in `scripts/lib/templates.js` and `$PilotGroup` in `scripts/Set-BaselineAssignment.ps1` — and
  run the pipeline again. Changing the group only in CIPP also works, but re-importing this file
  puts the default name back.
- **Link the ADE profiles.** `[Baseline] - Baseline-ADE-token` is deliberately not assigned: a macOS
  enrolment profile hangs off an ADE token, not an Entra group, and per token you pick one of
  the two.

## Defender-Office365.json — email protection

A second, separate baseline (`[Baseline] - Defender for Office 365`): Safe Links, Safe
Attachments, anti-phishing, anti-spam and anti-malware, Defender for SharePoint/OneDrive/Teams, and
the quarantine notification to users **every 4 hours** — the shortest Exchange allows. Separate
from `Baseline.json` because it needs Defender for Office 365 Plan 1 (Business Premium has it), so
you want to be able to assign it to other tenants. The values, with their reasoning, are in
[`scripts/lib/defender-office.js`](../scripts/lib/defender-office.js).

**Deliberately no preset policies.** Microsoft's Standard/Strict presets cannot be changed and
CIPP cannot measure them — so drift goes unseen. This baseline uses CIPP's own standards to create
custom policies at priority 0 for every accepted domain, at Strict level. CIS (2.1.x), ORCA and
CISA ScubaGear accept that as equivalent.

| | Value | Deviation from Strict |
|---|---|---|
| Quarantine notification | every 4 hours | — |
| Safe Links | email, Teams and Office; scan before delivery; internal mail too; no click-through | — |
| Safe Attachments | Block; SharePoint/OneDrive/Teams on; user is notified and can request release | Strict: admins only, no notification |
| Spam, high confidence spam, phish | quarantine, user is notified and releases it | — |
| High confidence phish, malware (attachment filter) | quarantine, admins only | — |
| Bulk | Junk from BCL 6 | Strict: quarantine from 5 — floods the notification |
| Phish threshold | 3 | Strict: 4 — many false positives |
| Spoof | Junk | Strict: quarantine; ORCA-112 recommends Junk |
| Impersonation, mailbox intelligence | quarantine with notification | — |
| Attachment filter | 53 default extensions plus scripts, OneNote, VHD and SVG | wider than Strict (part of CIS 2.1.11) |
| Outbound | 500 / 1000 / 1000, block | Strict: 400 / 800 / 800 |
| Teams | ZAP, file type and URL checks in chats | — |
| Admin notifications | malware from an internal sender, outbound spam (with copy), release requests — to `%SecurityAlertMail%` | not in Strict (CIS 2.1.3, 2.1.6) |

**Before the first run:** set the custom variable `SecurityAlertMail` in CIPP (Settings → Custom
Variables) — globally for *All Tenants*, with its own value per tenant where it must differ. The
admin notifications go there; without the variable those three standards fail. In the baseline
editor the `QuarantineRequestAlert` field only accepts an email address: if you save that field
there again, the editor wants a real address instead of the token.

**Per tenant, with [`scripts/Set-DefenderOfficeTenant.ps1`](../scripts/Set-DefenderOfficeTenant.ps1)**
— two things CIPP has no standard for:

- **Presets off.** A Standard or Strict preset takes precedence over these policies — and CIPP
  still reports *compliant*. The script turns the preset rules off; you can turn them back on in
  Defender.
- **VIPs, only when the customer names them.** By default a tenant has none. With
  `-VipGroupName` the members of that Entra group go into the anti-phishing policy
  (impersonation, max. 350). The group is the source: whoever leaves it also leaves the list. CIPP does not compare that
  list, so it does not overwrite it either. Run the script again when the group changes.

**Changing things in CIPP works, but in the right place:**

- **Per tenant** — a different address, an extension a customer needs, a standard that should not
  apply there: create an *override* on that standard for that tenant, or exclude the tenant. An
  override is stored apart from the baseline and survives a re-import.
- **For everyone** — changing or removing a standard: do it here, in `defender-office.js`. The
  CIPP editor can do it too (CIPP then marks the baseline with *local changes*), but the next
  import from this repo resets the baseline to this file.

If a `CIPP Default …` policy already exists, CIPP adopts it instead of creating a second one; it
keeps the old name.

Importing works as for `Baseline.json`: with the button. Updating: change
`defender-office.js` and run the script.

## Windows-Updates.json — patching

A third, separate baseline (`[Baseline] - Windows Updates`) for everything that updates a
Windows device: Windows itself, Edge, Microsoft 365 Apps and the other apps through winget.
Separate from `Baseline.json` because patching is something every tenant needs — including a
tenant that does not (yet) get the full Intune baseline. The layout lives in
[`scripts/lib/windows-updates.js`](../scripts/lib/windows-updates.js).

| Stage | Standard | Assignment | What it does |
|---:|---|---|---|
| 1 · Now | `[Baseline] - Updates-Ring3` | all devices, **except** `SEC-Update-Ring1` and `SEC-Update-Ring2` | Windows Update Ring 3 Production: installs at 13:00, two-day deadline |
| 1 · Now | `[Baseline] - Updates-SEC-Update-Ring1` | `SEC-Update-Ring1` | Ring 1 Pilot: updates right away |
| 1 · Now | `[Baseline] - Updates-SEC-Update-Ring2` | `SEC-Update-Ring2` | Ring 2 UAT: quality updates after three days |
| 1 · Now | `[Baseline] - Updates-Devices` | all devices | Edge Updates (restart required, outside working hours) and Microsoft Office Updates (automatic updates, cannot be turned off) |
| 2 · Winget-AutoUpdate | *Deploy Intune Application Template* | all devices (Required) | Winget-AutoUpdate: updates every app winget knows daily, except the [exclusion list](../IntuneTemplate/WIN/Apps/winget-autoupdate/README.en.md) |

Stage 2 starts once everything in stage 1 is compliant **and** two weeks have passed — the same
threshold as the pilot stage of `Baseline.json`.

**Ring 3 excludes the ring groups.** Without that exclusion a device in `SEC-Update-Ring1` gets
two update rings; Intune then reports a Conflict and applies the disputed settings (deferral,
deadline) through neither. A package shares its assignment with all its members, which is why
Ring 3 is a package of its own and the exclusion does not land on Edge and Office.

**These policies were taken out of `Baseline.json`.** They were in `Baseline-Devices` and
`Baseline-SEC-Update-Ring1/2`. A tenant on `Baseline.json` therefore needs this baseline *as
well*, otherwise nobody guards the update policies any more (they do stay in place: CIPP deletes
nothing). The Defender update rings, *Update Reports and Telemetry* and *Google Chrome Updates*
stay in `Baseline.json`.

**Winget-AutoUpdate arrives as an application template.** The standard only checks whether an
app with that name exists and takes the assignment from the template itself — it has no field of
its own for it. So it deploys
[`AppTemplate/Winget-AutoUpdate-AllDevices.json`](../AppTemplate/Winget-AutoUpdate-AllDevices.json),
the same app as `Winget-AutoUpdate.json` but assigned to all devices. The import button pulls that
template from this repo before the baseline itself (`referencedTemplates`). Two consequences:

- If WAU is already in the tenant (for instance deployed by hand to the pilot group), the
  standard sees it as present and does not change the assignment. Widen it to all devices yourself.
- If someone removes the assignment, CIPP does not notice: the app still exists.

**Before the first run:** the groups `SEC-Update-Ring1` and `SEC-Update-Ring2` must exist (empty
is fine), otherwise CIPP can neither assign nor exclude them. Licence: Intune only.

Importing works as for `Baseline.json`: with the button. Updating: a different layout in
`windows-updates.js`, the settings themselves in the policies in `IntuneTemplate/WIN/`; then run
`node scripts/set-packages.js` and the script below.

## Purview-DLP.json — data leakage

A fourth, separate baseline (`[Baseline] - Purview DLP`): Data Loss Prevention for Exchange,
SharePoint and OneDrive, as CIPP DLP templates from
[`DlpCompliancePolicyTemplate/`](../DlpCompliancePolicyTemplate/README.en.md). The choices are in
[`scripts/lib/purview-dlp.js`](../scripts/lib/purview-dlp.js).

| Stage | Policy | What it does |
|---:|---|---|
| 1 · Melden | `[Baseline] - DLP - Personal Data NL - Notify` | BSN, passport, driver's license or tax number going outside: policy tip for the user; in bulk (BSN 5+, the rest 10+) also an incident report and an alert to the admin |
| 1 · Melden | `[Baseline] - DLP - Personal Data BE - Notify` | Belgian national number, passport or driver's license number going outside: the same (national number 5+, the rest 10+), with a bilingual tip (nl/fr) |
| 1 · Melden | `[Baseline] - DLP - Financial - Notify` | credit or debit card number going outside: policy tip; in bulk (cards 10+, IBAN 20+) also report and alert |
| 2 · Blokkeren | `[Baseline] - DLP - Personal Data NL - Block` | the same bulk threshold: **blocks**, without override |
| 2 · Blokkeren | `[Baseline] - DLP - Personal Data BE - Block` | the same for the Belgian numbers |
| 2 · Blokkeren | `[Baseline] - DLP - Financial - Block` | the same for cards and IBANs |

"Outside" is always `AccessScope NotInOrganization`: mail to external recipients and files shared
with external people. Internal mail or sharing hits no rule at all.

**Stage 2 is manual, and that is the simulation.** The alerts from stage 1 have exactly the same
thresholds as the blocks in stage 2: what is in Purview → DLP → Alerts is exactly what stage 2
will stop. Go through that list (a payroll export to the accountant? Find another route first)
and only then move the tenant on. Stages stack, so in stage 2 the Notify policies keep alerting.

**No override.** CIPP's deploy path does not know `NotifyAllowOverride`, so "send anyway with a
reason" is not possible. That is why stage 2 only blocks bulk.

**Licence:** Business Premium is enough. Teams chat DLP and Endpoint DLP (USB, printing) need E5
or the Purview add-on and are deliberately left out. The built-in *Default Office 365 DLP policy*
(credit cards 1–9) can stay; turning it off avoids duplicate tips.

**Before the first run:** the CIPP app needs Security & Compliance permissions (the same as for
the other Purview standards). Alerts go to `SiteAdmin`; CIPP does not replace `%variables%` in
DLP templates, so set a mail address of your own per tenant in Purview.

**After the first deployment: write back once.** CIPP compares a template field by field with
what `Get-DlpComplianceRule` returns, and Purview fills in fields a hand-written template does not
have. If a tenant stays on *drift* while nothing changed, create a template from the deployed
policy in CIPP (Security → Compliance → DLP) and carry the differences into `purview-dlp.js`.

## Updating

Not by hand: run `node scripts/generate-baseline-template.js`. The packages and their
assignment follow from `fase` in [`_manifest.json`](../IntuneTemplate/_manifest.json) and the
target in [`_assignments.json`](../IntuneTemplate/_assignments.json); `--check` writes nothing and
fails when this file falls behind.

Be careful with re-exporting from CIPP: CIPP's own export flattens the packages into
separate template references, one per policy — a snapshot, after which a new policy no longer comes along
automatically. Generating in this direction keeps the late binding intact.
