# BaselineTemplate/

The CIPP **baseline** as a file: which packages deploy in which stage, to whom, and when a
tenant moves on.

| | |
|---|---|
| File | [`Baseline.json`](Baseline.json) — generated by [`scripts/generate-baseline-template.js`](../scripts/generate-baseline-template.js) |
| Recognised by | `TemplateType: "BaselineTemplate"` and the folder name `BaselineTemplate/` |
| Name in CIPP | `Baseline` |

## Why this lives here

`IntuneTemplate/` supplies the policies, but in CIPP templates just sit there: a baseline is
what deploys them. Filling in that screen by hand means adding the same standard thirteen times and
picking the right assignment target thirteen times — one misclick puts up to 69 policies (the
`CXNM - Standard - Baseline-Devices` package) on the wrong audience. So this file comes from the same source as the rest of the repo: the manifest.

## What's in it

| Stage | Packages | Moving on to this stage |
|---:|---|---|
| 1 · Now | `CXNM - Standard - Baseline-Devices`, `CXNM - Standard - Baseline-Users`, `CXNM - Standard - Baseline-ADE-token` and the eight group packages `CXNM - Standard - Baseline-SEC-*` | — stage 1 always applies |
| 2 · Pilot | `CXNM - Standard - Baseline-Pilot` | everything from stage 1 is compliant (`success`) **and** two weeks have passed (`time`) |
| 3 · Awaiting prerequisite | `CXNM - Standard - Baseline-Wacht` | `manual` — someone moves it on |

Which policies are in which package is listed in the
[`IntuneTemplate` README](../IntuneTemplate/README.en.md#cipp-packages).

Stage 1 always applies and later stages stack on top of it. The condition belongs to the stage
you **enter**, not the stage you leave. Phase 3 waits for something CIPP cannot measure — a
first phone enrolment — so `manual` is the honest answer there.

## Importing — with the button, not with the automatic sync

Tools → Community Repos → this repo → `BaselineTemplate/Baseline.json` → **Import**. CIPP
turns it into a baseline (not a template row) under Tenant Administration → Baselines.

It arrives assigned to the placeholder tenant `Exported Template`, so nothing deploys until you
pick tenants yourself. That is deliberate — it is the same placeholder CIPP's own export uses.

**That button is the only way.** CIPP has two code paths that read from a linked repo, and
only one of them knows about baselines:

| Path | What it does with this file |
|---|---|
| Tools → Community Repos → Import (`Invoke-ExecCommunityRepo`) | sees `TemplateType: "BaselineTemplate"` and calls `Import-CIPPBaselineTemplate` — becomes a baseline |
| The scheduled template sync (`New-CIPPTemplateRun`) | fetches every `.json` (except under `NativeImport`) and pushes it through `Import-CommunityTemplate`, without looking at `TemplateType` |

In that second path this file has no `RowKey`, no `@odata.type` and no `settings`, so it falls
through every detection and lands as a **nameless row** in the templates table — the same row
the other non-policy files in this repo end up in (deduplication matches on an empty
`Displayname`, so it stays that one row). It does nothing and you can delete it in CIPP.

Consequence for day-to-day use: the policies in `IntuneTemplate/` come along automatically with
the link, the baseline itself you fetch once with the button — and again when it changes, which
the catalogue flags with *UpdateAvailable*. A re-import updates the existing baseline on the
same GUID, so the assigned tenants and the results stay in place.

Putting it under a `NativeImport` path to avoid that nameless row does not work: the catalogue
filters that word out too, and then the file can no longer be found with the button either.

## What you do yourself afterwards

- **Assign tenants.** Without that the baseline runs nowhere.
- **Make sure the groups exist.** `SEC-Baseline-Pilot`, `SEC-Update-Ring1`, `SEC-Update-Ring2`,
  `SEC-Shared-Devices`, `SEC-Android-Dedicated`, `SEC-iOS-BYOD`, `SEC-iOS-Corporate` and
  `SEC-Remote-Support-macOS` must exist in the tenant; CIPP looks them up by name (wildcards allowed).
  These are default names. If a group is called something else, change `faseGroep` in
  [`_manifest.json`](../IntuneTemplate/_manifest.json) — for the pilot group also `PILOT_GROUP`
  in `scripts/lib/templates.js` and `$PilotGroup` in `scripts/Set-BaselineAssignment.ps1` — and
  run the pipeline again. Changing the group only in CIPP also works, but re-importing this file
  puts the default name back.
- **Link the ADE profiles.** `CXNM - Standard - Baseline-ADE-token` is deliberately not assigned: a macOS
  enrolment profile hangs off an ADE token, not an Entra group, and per token you pick one of
  the two.

## Updating

Not by hand: run `node scripts/generate-baseline-template.js`. The packages and their
assignment follow from `fase` in [`_manifest.json`](../IntuneTemplate/_manifest.json) and the
target in [`_assignments.json`](../IntuneTemplate/_assignments.json); `--check` writes nothing and
fails when this file falls behind.

Be careful with re-exporting from CIPP: CIPP's own export flattens the packages into
separate template references, one per policy — a snapshot, after which a new policy no longer comes along
automatically. Generating in this direction keeps the late binding intact.
