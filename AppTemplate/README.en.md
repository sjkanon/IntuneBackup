# AppTemplate/

CIPP **application templates**: Win32 apps that CIPP puts into a tenant by itself, without anyone
having to upload an `.intunewin`.

| File | App | Source |
|---|---|---|
| [`Winget-AutoUpdate.json`](Winget-AutoUpdate.json) | `[Baseline] - WIN - D - Winget-AutoUpdate` | [`IntuneTemplate/WIN/Apps/winget-autoupdate/`](../IntuneTemplate/WIN/Apps/winget-autoupdate/README.en.md) |
| [`Winget-AutoUpdate-AllDevices.json`](Winget-AutoUpdate-AllDevices.json) | the same app, assigned to all devices — for the baseline [`Windows-Updates.json`](../BaselineTemplate/README.en.md#windows-updatesjson--patching) | same |

## How it works

CIPP cannot template an installer package of your own, but it can template a *Custom Application*
(Win32 script app): CIPP uploads a small placeholder package of its own and runs a PowerShell
script as the installer. So the install script fetches the installer itself — pinned and with a
hash check. The template carries only scripts.

Each file is a CIPP table row (`PartitionKey: AppTemplate`) and is generated by
[`scripts/generate-app-templates.js`](../scripts/generate-app-templates.js) from the scripts in
[`IntuneTemplate/WIN/Apps/`](../IntuneTemplate/WIN/Apps/winget-autoupdate/README.en.md). Make changes there, not here.

## Deploying

1. CIPP → **Tools → Community Repos** → this repo → the file → **Import**.
2. **Applications → Application Templates** → the template → **Deploy**, with tenants and
   assignment. Or in a baseline with the standard *Deploy Intune Application Template*.

The templates assign nothing themselves: you choose the assignment when deploying, because a
phase 2 app goes to the pilot group first.
